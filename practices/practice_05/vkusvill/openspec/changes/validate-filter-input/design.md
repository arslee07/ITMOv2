# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/shop-filtering/spec.md`.

Текущее состояние:

- Все три обработчика (`HandleIndex`, `HandleShops`, `HandleShopsPoints`) начинают
  с вызова `parseQueryParams`, который не возвращает ошибок и подменяет мусор
  нулями.
- `buildPageData` сразу идёт в `StoreCache` и MCP-клиент, поэтому валидация должна
  стоять строго до него, иначе лимит 60 req/min расходуется впустую.
- Ошибки уже отдаются через `http.Error` (простой текст, код 500).
- Go-тесты проекта табличные, без внешних зависимостей и без сети.

## Goals / Non-Goals

**Goals:**

- Одна точка разбора и проверки параметров для всех трёх обработчиков.
- Ошибка называет параметр и причину; ни одного обращения к MCP при отказе.
- Нулевые изменения поведения для валидных запросов.

**Non-Goals:**

- Не менять формат успешных ответов и клиентский рендеринг.
- Не вводить общий middleware валидации и сторонние библиотеки.
- Не валидировать заголовки, тело запроса и параметры, которых нет в контракте.

## Decisions

**D1. Валидация внутри `parseQueryParams`, а не middleware.**
`parseQueryParams` уже единственная точка разбора, поэтому меняем сигнатуру на
`(mcp.QueryParams, error)`. Альтернатива — middleware с белым списком параметров:
даёт больше кода и не знает про смысл конкретных полей (например, парность
`lat`/`lon`).

**D2. Типизированная ошибка `ValidationError{Param, Message}`.**
Обработчики приводят её к `400` через общий хелпер, остальные ошибки остаются
`500`. Альтернатива — `fmt.Errorf` со строкой: нельзя надёжно отличить ошибку
ввода от сбоя MCP.

**D3. Ответ — `text/plain; charset=utf-8` через `http.Error`.**
Совпадает с текущим стилем обработчиков, читается и человеком, и curl, не
требует нового формата ошибок в JSON-контракте. Важно: в текущих шаблонах нет
`hx-get`/`hx-target`, то есть HTMX-обмена с `/shops` сейчас не происходит, а на
`GET /` ошибка отдаётся как текст вместо страницы — это осознанно принимаем, UI не
меняем. Альтернатива — JSON `{error: ...}`: пришлось бы учить клиент разбирать два
формата.

**D4. Правила приводятся к одной таблице проверок по параметру.**
Явные имена параметров в сообщениях, пустая строка трактуется как «параметр не
задан» — это совместимо с текущими ссылками. `page` сохраняет прежнее приведение
(`< 1` → `1`), но нечисловое и дробное значение отвергается.

**D5. Наличие геолокации определяется отдельным признаком `HasLocation`.**
Сейчас `buildPageData` проверяет `UserLat != 0 && UserLon != 0`, из-за чего точка
`0,0` молча выпадает из сортировки. Добавляем в `mcp.QueryParams` поле
`HasLocation bool`, выставляемое при разборе по факту передачи пары; проверки
координат читают его. Альтернатива — `*float64`: меняет публичные типы пакета `mcp`
и сериализацию, избыточно для одной проверки.

**D6. `scope=all` не валидируется.**
`HandleShopsPoints` при `scope=all` отдаёт накопленный кэш и не использует фильтры,
поэтому разбор параметров туда не попадает — это явная граница, зафиксированная в
spec, а не недосмотр.

**D7. Клиентский признак наличия координат.**
В `app.js` наличие геолокации проверялось как `f.lat && f.lon`, поэтому `0,0`
выключал сортировку в браузере. В `currentFilters` добавлен `hasCoords` по факту
заполнения скрытых полей, и клиентские проверки переходят на него. Hidden-поля
`filter-lat`/`filter-lon` заполняются только кнопкой геолокации, поэтому URL-пара
`?lat=&lon=` до клиента не доходит — это существующее ограничение, в границы
изменения не входит.

**D8. Длина `q` считается в рунах (`utf8.RuneCountInString`), управляющими
считаются коды `< 32` и `127`.**
Иначе кириллический запрос упирался бы в лимит втрое раньше, а `\t` из вставки
из буфера ломал бы поиск.

## Risks / Trade-offs

- [Ранее «битые» ссылки молча работали как «без фильтра»] → ломаем это намеренно;
  пустые значения и отсутствие параметров остаются валидными, в отчёте фиксируем
  изменение поведения.
- [Введение `HasLocation` меняет структуру `mcp.QueryParams`] → поле аддитивное,
  сериализация наружу не используется; проверяется тестом на `lat=0&lon=0`.
- [Дублирование кода ответа в трёх обработчиках] → один хелпер
  `writeValidationError`, тесты на все три маршрута.
- [Список и точки используют один признак наличия координат] → серверный
  `HasLocation` и клиентский `hasCoords` введены одновременно, тест на `lat=0&lon=0`
  и ручная проверка в браузере.
- [Порядок точек в JSON не сортируется по расстоянию] → списку это не нужно,
  карта игнорирует порядок; сценарий в spec явно ограничен `/` и `/shops`.
- [Проверка `q` в двух местах: сервер и клиент] → серверная проверка
  авторитетна, клиентское ограничение `maxlength` добавляется отдельной задачей
  только если останется время; в границах изменения — сервер.

## Migration Plan

Изменение обратно совместимо для валидных запросов, миграция данных не нужна.
Откат — revert коммита с валидацией; кэш и MCP-клиент не затрагиваются.
