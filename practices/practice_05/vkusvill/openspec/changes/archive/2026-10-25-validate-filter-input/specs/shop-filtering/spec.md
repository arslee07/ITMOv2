# Spec Delta

## Purpose

Проверять query-параметры фильтра магазинов до обращения к кэшу и MCP: корректный
ввод сохраняет прежнее поведение, некорректный — даёт понятную ошибку 400 и не
расходует лимит внешнего API.

## ADDED Requirements

### Requirement: Область применения валидации

Проверка SHALL применяться к `GET /`, `GET /shops` и `GET /api/shops/points`.
Пустое значение параметра (`?city_id=`) MUST трактоваться как «параметр не задан».
Запрос `GET /api/shops/points?scope=all` MUST NOT валидировать параметры фильтра:
этот режим отдаёт накопленный кэш и игнорирует фильтры.

#### Scenario: Пустое значение равно отсутствию параметра
- **WHEN** запрос содержит `city_id=` и `q=`
- **THEN** ответ успешный, город и поиск не фильтруются

#### Scenario: Режим scope=all вне валидации
- **WHEN** запрос содержит `scope=all&lon=200`
- **THEN** ответ успешный, параметры фильтра игнорируются

### Requirement: Валидация числовых идентификаторов

Параметры `city_id`, `feature_id`, `region_id`, `subway_id` SHALL принимать только
целые неотрицательные числа. Отсутствующий или пустой параметр MUST означать «без
фильтра» (значение 0), как и раньше.

#### Scenario: Нечисловой идентификатор отвергается
- **WHEN** запрос содержит `feature_id=coffee`
- **THEN** ответ `400`, в сообщении указан параметр `feature_id`

#### Scenario: Отрицательный идентификатор отвергается
- **WHEN** запрос содержит `city_id=-5`
- **THEN** ответ `400`, в сообщении указан параметр `city_id`

#### Scenario: Нулевой идентификатор допустим
- **WHEN** запрос содержит `subway_id=0`
- **THEN** ответ успешный, фильтр по метро не применяется

#### Scenario: Дробный идентификатор отвергается
- **WHEN** запрос содержит `region_id=1.5`
- **THEN** ответ `400`, в сообщении указан параметр `region_id`

### Requirement: Валидация номера страницы

`page` SHALL принимать только целое число. Отсутствие параметра или значение
меньше 1 MUST приводить к первой странице, как и раньше. Нецелое или нечисловое
значение MUST отвергаться.

#### Scenario: Нулевая страница приводится к первой
- **WHEN** запрос содержит `page=0`
- **THEN** ответ успешный и соответствует запросу без параметра `page`

#### Scenario: Нечисловая страница отвергается
- **WHEN** запрос содержит `page=abc`
- **THEN** ответ `400`, в сообщении указан параметр `page`

#### Scenario: Дробная страница отвергается
- **WHEN** запрос содержит `page=1.5`
- **THEN** ответ `400`, в сообщении указан параметр `page`

### Requirement: Валидация координат пользователя

`lat` и `lon` SHALL передаваться только вместе, быть конечными числами и лежать в
пределах `-90..90` и `-180..180`. Наличие координат MUST определяться по факту
передачи пары, а не по неравенству нулю: `lat=0&lon=0` — валидная точка. Частично
заданные координаты MUST отвергаться. Если пара передана, ответ
`/api/shops/points` MUST содержать рассчитанное расстояние до каждого магазина
(`distance_str`).

#### Scenario: Координаты переданы парой
- **WHEN** запрос содержит `lat=55.75&lon=37.62`
- **THEN** ответ успешный, у каждой точки в ответе заполнено `distance_str`

#### Scenario: Нулевые координаты допустимы
- **WHEN** запрос содержит `lat=0&lon=0`
- **THEN** ответ успешный, нулевые координаты считаются заданными и `distance_str` заполнено

#### Scenario: Только одна координата
- **WHEN** запрос содержит `lat=&lon=37.62`
- **THEN** ответ `400`, в сообщении указано, что нужны обе координаты

#### Scenario: Координата вне диапазона
- **WHEN** запрос содержит `lat=95&lon=37.62`
- **THEN** ответ `400`, в сообщении указан параметр `lat`

#### Scenario: Нечисловая координата
- **WHEN** запрос содержит `lat=NaN&lon=37.62`
- **THEN** ответ `400`, в сообщении указан параметр `lat`

### Requirement: Валидация поисковой строки

Поисковая строка `q` SHALL обрезаться по краям, содержать не более 100 рун и не
содержать управляющих символов (коды меньше 32 и 127). Некорректная строка MUST приводить к ошибке 400,
а не к «тихому» пустому результату.

#### Scenario: Пробелы по краям обрезаются
- **WHEN** запрос содержит `q=%20%20Пятёрочка%20`
- **THEN** поиск выполняется по строке `Пятёрочка`

#### Scenario: Слишком длинная строка отвергается
- **WHEN** длина `q` после обрезки превышает 100 рун
- **THEN** ответ `400`, в сообщении указан параметр `q`

#### Scenario: Управляющие символы отвергаются
- **WHEN** `q` содержит символ с кодом меньше 32 (например, `\t`) или 127
- **THEN** ответ `400`, в сообщении указан параметр `q`

### Requirement: Контракт ошибки ввода

При некорректных параметрах сервис MUST отвечать `400 Bad Request` с типом
`text/plain; charset=utf-8` и сообщением на русском языке, содержащим имя
параметра и причину. Такой запрос MUST NOT обращаться к MCP-серверу ВкусВилл.

#### Scenario: Ошибка содержит имя параметра
- **WHEN** запрос содержит `city_id=abc`
- **THEN** тело ответа содержит `city_id` и код ответа равен `400`

#### Scenario: Некорректный запрос не расходует лимит MCP
- **WHEN** запрос отклонён валидацией
- **THEN** ни один HTTP-запрос к MCP не выполняется

#### Scenario: Ошибка валидации у JSON-эндпоинта
- **WHEN** `GET /api/shops/points` содержит `lon=200`
- **THEN** ответ `400` с текстовым сообщением, JSON-тело не возвращается

### Requirement: Совместимость с прежним поведением

Для валидных запросов поведение MUST оставаться прежним: отсутствие параметров
отдаёт первую страницу без фильтров, успешные ответы не меняют формат и не
добавляют полей, кроме уже существующего `distance_str` при переданных координатах.

#### Scenario: Запрос без параметров
- **WHEN** запрос не содержит ни одного параметра фильтра
- **THEN** ответ успешный, фильтры не применяются
