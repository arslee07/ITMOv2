# Сравнение SDD-фреймворков: OpenSpec 1.14.1 и Spec Kit 1.1.3

Обе фичи («валидация фильтра» и «экспорт CSV») сделаны на одном и том же проекте,
поэтому сравнение — не по документации, а по опыту применения.

## Форма работы

| | OpenSpec | Spec Kit |
|---|---|---|
| Единица работы | change (`openspec/changes/<id>`) | feature-ветка + `specs/001-…` |
| Артефакты | proposal, delta specs, design, tasks | constitution, spec, plan, tasks |
| Спеки | дельта (`ADDED/MODIFIED/REMOVED`) к main spec | полная спека фичи, main spec не ведётся |
| Команды | `opsx-*` через CLI `openspec` | `/speckit.*` в клиенте |
| Проверка структуры | `openspec validate --strict` | нет встроенного валидатора |
| Завершение | `archive` переносит дельту в main spec | нет архива; спека остаётся в `specs/` |
| Настройка под проект | `openspec/config.yaml` (`rules`, `context`) | `.specify/memory/constitution.md` + шаблоны |

## Что понравилось в OpenSpec

- **Brownfield по умолчанию**: change живёт рядом с кодом, дельта не переписывает
  main spec, а `archive` собирает итог. Для существующего проекта это дешевле.
- **`validate --strict`** ловит ошибки формы (сценарии без 4 решёток, длинные
  описания) до реализации.
- **Правила в конфиге** действуют на все будущие изменения без копирования
  инструкций в чат (часть 2 практики).
- **Мало артефактов**: 4 файла на фичу, при желании `design` можно не делать.

## Что понравилось в Spec Kit

- **Конституция проекта** — правила (stdlib, тесты, доступность) читаются агентом
  до плана; в OpenSpec аналогичное приходится держать в `context`/AGENTS.md.
- **Жёсткая последовательность** spec → plan → tasks → implement снижает
  вероятность прыжка в код.
- **Готовые команды** на все шаги, включая clarify/analyze/checklist — полезно,
  когда требований много и они противоречивы.

## Ограничения, которые всплыли

- Spec Kit заточен под «одна фича — одна спека». Две команды (UI и логика) в
  одной фиче пришлось эмулировать двумя файлами внутри одной feature-папки и
  общим контрактом; фреймворк такую схему не описывает.
- У Spec Kit нет аналога `archive`: история изменений спеки остаётся только в git,
  а «текущего» свода требований по системе нет.
- Spec Kit инициализирует `specs/` и `.specify/` в корне и добавляет свои
  команды в `.opencode/`; с OpenSpec они сосуществуют, но смешивают два набора
  команд в одном клиенте.
- OpenSpec-команды ориентированы на CLI-статус (`openspec status`), Spec Kit — на
  чтение шаблонов; во втором случае больше контекста уходит в диалог.

## Вывод

- **Новая фича в живом проекте, нужна трассируемость требований** → OpenSpec:
  дельта + архив + валидатор.
- **Новый продукт или несколько команд с ролями, важна конституция и поэтапность**
  → Spec Kit.
- Смешивать оба в одном репозитории можно, но лучше выбрать один как основной:
  иначе два набора команд и две «правды» о требованиях.
