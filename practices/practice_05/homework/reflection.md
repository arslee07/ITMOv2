# Рефлексия — ДЗ 5

## Что согласовали

Главный стык двух команд — **где рождается файл**. Команда UI исходила из того,
что данные уже в браузере (`allShops`), и предлагала собирать CSV на клиенте.
Команда логики настаивала на серверном endpoint: фильтрация и форматирование
расстояния уже есть на сервере, а браузерный вариант пришлось бы дублировать.
Согласовали endpoint: клиент только передаёт активные фильтры и скачивает blob.
Это же решение убрало второй спор — кто экранирует `;` и кавычки: остался один
`encoding/csv`.

Второй содержательный стык — **что считать «видимыми» магазинами**. UI рисует не
больше 500 карточек и считал, что экспорт должен совпадать с ними. Логика отдаёт
весь кэш. Договорились: «видимые» — это выборка по фильтрам, а лимит карточек —
деталь отрисовки; файл может быть больше списка. Формулировку поправили в обеих
спеках и в SC-002, иначе приёмка была бы по разным критериям.

Третий — формат. Разделитель `;`, BOM, CRLF и пустые поля вместо `null` — это
уступки логики в пользу «открыть в Excel двойным кликом». UI отказался от идеи
самостоятельно считать расстояние.

## Где пришлось вмешаться человеку

- Выбор между клиентским и серверным экспортом: агенты предлагали каждый своё,
  решение принимал я по критерию «одна реализация правил».
- Лимит 20 000 строк и код `413` — продуктовая договорённость, из кода её не
  вывести.
- После перекрёстного ревью: `region_id`/`subway_id` были в контракте, но не в
  коде. Можно было убрать их из контракта, но фильтры уже заявлены в API — выбрал
  доделать фильтрацию, а не сокращать контракт.
- Сортировка магазинов без координат: формально они «дальше всех», фактически
  расстояние неизвестно. Решил отправлять их в конец с пустой ячейкой.

## Чему научился

1. **Контракт должен описывать стык, а не повторять спеки.** Пока команды
   писали «как удобно», расхождения были в четырёх местах; после контракта
   осталось одно — объём выборки.
2. **Формулировка «видимые» — ловушка.** Одно слово скрывало разницу между
   «нарисовано 500 карточек» и «подходит под фильтр». Такие слова надо
   разворачивать в критерий проверки сразу.
3. **Ревью отдельным чатом работает.** Он нашёл два реальных бага (сортировка от
   нулевых координат и непокрытые фильтры), которые автор кода не видел, потому
   что проверял по своей же спеке.
4. **Разные фреймворки дают разную дисциплину.** OpenSpec удобнее для brownfield:
   дельта и архив. Spec Kit лучше держит рамку «спека → план → задачи», но не
   умеет вести текущий свод требований и не поддерживает две спеки на одну фичу —
   пришлось добавлять контракт руками.
5. **Автотесты дешевле ручной проверки, но не заменяют её.** Серверные сценарии
   закрыты табличными тестами, а состояния кнопки остались на ручную демонстрацию:
   в проекте нет браузерного раннера, и добавлять его ради одной кнопки
   несоразмерно.
