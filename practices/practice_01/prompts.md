## Master Prompt v1

Соберите здесь контракт второго запуска. Не копируйте все документы целиком — ставьте ссылки на файлы и переносите только необходимый для задачи контекст.

### 1. Цель и роль

- Цель: по `TRAINING_PR.diff` вернуть краткий обзор изменений, ≤3 риска и список проверок.
- Роль AI: ии-ревьювер, анализирует только предоставленный diff и правила.

### 2. Входы и источники

- Обязательный вход: `TRAINING_PR.diff`.
- Разрешённые файлы и источники: `TRAINING_PR.diff`; правила из `CASE.md` (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1).
- Context Pack — факты, правила, примеры и ограничения: см. `context.md` этого задания.

### 3. Задача и артефакты

- Что сделать: проанализировать diff, сопоставить с правилами SEC-1…QA-1 и обнаружить риски, подтверждённые строками diff или правилами.
- Что вернуть: JSON-структуру в тексте ответа с полями `summary`, `risks` (≤3 элемента: `file`, `line`, `evidence`, `risk`, `rule`) и `checks` (список воспроизводимых проверок).

### 4. Формат результата

- Структура ответа: сначала summary (1-2 предложения), затем до 3 рисков в формате candidate → evidence → check, затем список проверок.
- Ограничения объёма: не более 10 пунктов в `checks`.

### 5. Полномочия и запреты

- Разрешено: анализировать diff, ссылаться на правила, предлагать проверки.
- Запрещено: approve, merge, edit код; придумывать новые правила; вывод за пределы diff и CASE.md.

### 6. Рабочий процесс и остановка

- Шаги: прочитать diff; сопоставить изменения с правилами; сформировать summary; отобрать ≤3 подтверждённых риска; добавить проверки.
- Когда остановиться и запросить человека: если требуется информация вне diff/CASE.md или нужна политика безопасности, не описанная правилами.

### 7. Проверки и evidence

- Как проверять утверждения: каждое утверждение подтверждать ссылкой на строку diff или конкретным правилом из CASE.md (QA-1).
- Какое evidence сохранить: цитату кода из diff и координаты `file:line` для каждого риска.

### 8. Definition of Done

- Задача закончена, когда: выдан summary, ≤3 риска с candidate/evidence/check и список checks, все риски ссылаются на файл:строка и правило.

## Сравнение двух запусков

| Проверка | Zero-shot | С master prompt | Вывод команды |
|---|---|---|---|
| Есть ссылка на файл или строку | Неточные ссылки или широкие диапазоны (app/review_service.py:19-22) | Точечная адресация конкретных строк (app/review_service.py:20, 21, 22) | Во втором запуске точность ссылок значительно выше |
| Вывод подтверждён diff или правилом | Часть замечаний строилась на догадках и общих советах («добавьте тесты») | Все 3 риска строго доказаны цитатой из diff и привязаны к правилам SEC-1, REL-1, OUT-1 | Соответствует QA-1 во втором запуске |
| Соблюдены границы AI | Размытые границы, рассуждения об архитектуре в целом | Строгое удержание роли: только советник, без approve/merge и без генерации кода | Границы соблюдены во втором запуске |
| Есть воспроизводимая проверка | Абстрактные фразы («проверить секреты», «протестировать ошибки») | Пошаговые сценарии воспроизведения (мок LLM с логом prompt, sleep 15s, вызов с dummy payload) | Есть чёткие шаги воспроизведения во втором запуске |

## P1-01

Summary

Добавлен сервис ревью: FastAPI эндпоинт POST `/api/reviews` вызывает `ReviewService.review`, который отправляет сырой diff во внешний LLM и возвращает в ответ только поле `comment`.

Risks (≤3), формат candidate → evidence → check

1) Candidate (SEC-1): секреты из diff могут утечь во внешний LLM, т.к. нет редактирования перед отправкой.
   Evidence: app/review_service.py:19-22 —
   «prompt = f"Review this pull request and find problems:\n{diff}"; answer = self.llm.generate(prompt)» — сырое встраивание diff без удаления секретов. Правило: SEC-1.
   Check: передать diff с тестовым «token=abcd1234» и убедиться, что перед отправкой в LLM вместо значения подставляется [REDACTED].

2) Candidate (REL-1): отсутствие таймаута и контролируемой обработки ошибок для внешнего LLM.
   Evidence: app/review_service.py:21 — вызов `self.llm.generate(prompt)` без таймаута; app/api.py:35-38 — `create_review` не перехватывает исключения, ошибка вернёт 500. Правило: REL-1 (таймаут 10s и контролируемый ответ).
   Check: эмулировать зависание клиента LLM >10s и ожидать контролируемый ответ сервиса (например, 503) без трассировки стека в теле.

3) Candidate (OUT-1): ответ сервиса не соответствует контракту (нет summary/risks/checks, только `comment`).
   Evidence: app/review_service.py:22 — `return {"comment": answer}`; app/api.py:36-38 — просто проксирует этот dict. Правило: OUT-1 (ответ содержит summary, risks, checks).
   Check: интеграционный вызов POST `/api/reviews` и проверка, что ответ соответствует схеме OUT-1: поля `summary`, `risks` (≤3, с file/line/evidence/risk), `checks`.

Checks (общие)

- Тест на SEC-1: подать diff с имитацией секретов (token/password/private key) и проверить редакцию.
- Тест на REL-1: замедлить/уронить LLM‑клиент, проверить таймаут 10s и контролируемый ответ.
- Тест на OUT-1: контракт ответа соответствует требуемой структуре.

## P1-02

Summary: PR добавляет эндпоинт POST /api/reviews и метод ReviewService.review, который отправляет сырой diff во внешний LLM и возвращает один текстовый «comment».

Risks:
- file:line: app/review_service.py:20
  evidence: prompt = f"Review this pull request and find problems:\n{diff}"
  risk: Сырой diff отправляется во внешний LLM без очистки секретов. Нарушение SEC-1 (нет удаления токенов/паролей/ключей из diff перед внешним LLM-вызовом).
- file:line: app/review_service.py:21
  evidence: answer = self.llm.generate(prompt)
  risk: Нет таймаута и контролируемой обработки ошибок внешнего LLM-вызова. Нарушение REL-1 (требуется таймаут 10 секунд и преобразование ошибки в контролируемый ответ).
- file:line: app/review_service.py:22
  evidence: return {"comment": answer}
  risk: Формат ответа не соответствует требованию OUT-1 (должны быть summary, risks, checks; сейчас возвращается только «comment»).

Checks:
- SEC-1: Отправка секрета в LLM.
  1. Запустить сервис и подменить зависимость LLM на мок, который логирует полученный prompt.
  2. Вызвать POST /api/reviews с телом {"diff": "code\n-----BEGIN PRIVATE KEY-----\n..."}.
  3. Проверить лог мока: убедиться, что секретная строка присутствует в prompt без маскировки (подтверждает нарушение SEC-1).
- REL-1: Проверка таймаута 10 секунд и контролируемого ответа.
  1. Подменить LLM.generate на функцию, которая делает sleep 15 секунд и затем возвращает ответ.
  2. Вызвать POST /api/reviews с любым diff.
  3. Замерить длительность ответа и результат: если ответ приходит после >10 секунд и/или возвращается необработанная ошибка/нет контролируемого ответа, риск подтвержден (нарушение REL-1).
- OUT-1: Валидация формата ответа.
  1. Вызвать POST /api/reviews с телом {"diff": "dummy"}.
  2. Проверить JSON-ответ: он содержит только ключ "comment" и не содержит "summary", "risks", "checks" — несоответствие OUT-1 подтверждено.
