## Context Pack для первого рабочего сценария

### Факты и правила

- По diff добавлены:
  - app/review_service.py:19-22 — метод ReviewService.review формирует промпт с сырым diff и вызывает llm.generate.
  - app/api.py:35-38 — эндпоинт POST /api/reviews принимает произвольный dict payload и вызывает review_service.review(payload["diff"]).
- Правила репозитория, влияющие на этот PR (см. CASE.md):
  - SEC-1: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
  - API-1: diff длиннее 20 000 символов отклоняется с HTTP 413.
  - REL-1: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
  - OUT-1: ответ помощника содержит summary, массив risks (≤3) и массив checks; в risks обязательны file, line, evidence, risk.
  - QA-1: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.
  - SCOPE-1: сервис только советует; он не пишет код и не выполняет действия в GitHub.

### Формат входа и результата

- Вход для помощника: TRAINING_PR.diff и правила из CASE.md (SEC-1…QA-1).
- Результат: summary + до 3 рисков (file:line, evidence из diff, ссылка на правило) + список проверок (checks).

### Ограничения и запрещённые действия

- Не придумывать правил сверх CASE.md.
- Не approve, не merge, не редактировать код (SCOPE-1).
- Включать риск только при наличии evidence из diff или правила (QA-1).

### Хороший пример

app/review_service.py:19-22 — diff отправляется во внешний LLM без удаления секретов, что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться, что в prompt осталось [REDACTED].

### Плохой пример

Код можно улучшить. Добавьте тесты и обработку ошибок.

### Что пока неизвестно

- Будет ли добавлена валидация входа через Pydantic и ограничение размера тела запроса.
- Какая стратегия редактирования/редакции секретов перед LLM.
- Какой ожидаемый формат контролируемой ошибки при таймауте LLM.
