# ADR: Архитектура сервиса AI-помощника ревьюера PR

- Статус: accepted
- Дата: 2026-09-20
- Ответственные: Команда разработки AI-ассистента

## Контекст

Текущая реализация сервиса ревью (TRAINING_PR.diff) имеет критические архитектурные и
эксплуатационные проблемы:
1. Сырой diff передаётся во внешний LLM без очистки секретов, создавая риск компрометации токенов и
ключей (нарушение SEC-1).
2. Вызов внешнего LLM не ограничен таймаутом и не перехватывает сбои, что приводит к зависанию
запросов и HTTP 500 (нарушение REL-1).
3. Формат ответа возвращает неструктурированный comment вместо структурированного контракта с
доказательной базой (нарушение OUT-1).
4. Отсутствует лимит размера входящего diff (нарушение API-1).

## Решение

Принята архитектура легковесного прокси-сервиса с жестким контролем границ и пайплайном обработки:
1. **API Gateway / Валидация:** FastAPI-эндпоинт `POST /api/reviews` проверяет размер входящего тела
  (HTTP 413, если diff > 20 000 символов согласно API-1).
2. **Санитизация (Sanitizer):** Перед сборкой промпта diff проходит через фильтр секретов, заменяя
  токены, приватные ключи и пароли на `[REDACTED]` (SEC-1).
3. **LLM Client с изоляцией:** Запрос к внешнему LLM отправляется с контролируемым таймаутом 10
  секунд. При превышении или ошибке провайдера сервис возвращает контролируемый HTTP 503 без утечки
  системных логов (REL-1).
4. **Парсинг и валидация контракта:** Ответ модели парсится и валидируется через Pydantic-схему:
  `summary` (строка), `risks` (массив ≤3 элементов с `file`, `line`, `evidence`, `risk`), `checks`
  (массив строк) согласно OUT-1.
5. **Ограничение прав (Guardrails):** Сервис функционирует исключительно как советник (advisory
  mode) без интеграции с правами записи в GitHub (SCOPE-1).

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Прямой вызов LLM из GitHub Actions без бэкенд-сервиса | Не позволяет централизованно применять
  фильтрацию секретов (SEC-1), вести аудит и контролировать схему ответов |
| Автономный агент с правами на запись и commit/merge | Нарушает SCOPE-1, несёт высокий риск
  деструктивных изменений в кодовой базе без предварительного аппрува инженера |
| Локальная LLM внутри сервиса | Требует выделенной GPU-инфраструктуры; на этапе прототипа проще и
  дешевле использовать внешний LLM с защитным контуром |

## Последствия и главный риск

- Положительные последствия: Гарантированная защита от утечки секретов (SEC-1), устойчивость к
  падениям провайдера LLM (REL-1), машиночитаемый структурированный результат (OUT-1).
- Ограничения: Diff ограничен 20k символами (крупные PR требуют предварительной декомпозиции).
- Главный риск: Галлюцинации LLM и генерация ложноположительных рисков.
- Как проверим риск: Правило QA-1 (каждый риск обязан содержать цитату кода и file:line), а также
  обязательная проверка предложенных шагов верификации (checks) человеком-ревьюером.

```mermaid
    subgraph LLM_Boundary[Внешний контур LLM]
        PromptBuilder -->|POST с таймаутом 10s| LLMClient[LLM Provider]

        LLMClient -->|Сырой ответ| Parser[4. Schema Validator OUT-1]
    end

    Parser -->|Валидный JSON: summary, risks <=3, checks| Client
```
